# PeerSpan 可行性分析

调研日期：2026-07-31

## 1. 需求的准确表达

这个想法本质上不是“把软件迁移到另一台电脑”，而是把应用的**显示表面**投送到另一台电脑，再把鼠标、键盘等输入送回应用实际运行的电脑。

以 A 上的应用显示到 B 为例：

- A 保有进程、内存、CPU/GPU 计算、磁盘文件和网络连接。
- A 采集窗口或一块虚拟显示器的画面并编码。
- B 解码画面，在全屏画布或代理窗口中显示。
- B 将鼠标、键盘、滚轮、剪贴板等事件回传给 A。
- A 把输入映射到原窗口，所以用户感觉是在 B 上直接操作。

A、B 安装相同程序后，任一台都可以临时充当来源端或接收端。所谓“互为扩展屏”是两个对等会话的组合，不是让两个 Windows 内核真的共享一套桌面对象。

## 2. GitHub 上已有的相近项目

下表中的星标数量只是调研当日的量级快照，会随时间变化。

| 项目 | 已解决的部分 | 与 PeerSpan 的差距 |
| --- | --- | --- |
| [Deskreen](https://github.com/pavlobu/deskreen)（约 21.2k） | Electron + WebRTC，把电脑屏幕串流到任意带浏览器的设备，产品定位就是网络第二屏 | 社区版 README 主要描述实时画面流；不是 Windows 原生的双向代理窗口，也没有完整的跨边缘窗口交接模型 |
| [Sunshine](https://github.com/LizardByte/Sunshine)（约 39.8k）+ [Moonlight](https://github.com/moonlight-stream/moonlight-qt)（约 18.1k） | 成熟的低延迟画面、音频和输入传输，支持 AMD/Intel/NVIDIA 硬件编码 | 面向整块桌面或游戏/应用串流；远端仍是一个视频画布，不会成为可与本机窗口混排的原生代理窗口 |

| [parsec-vdd](https://github.com/nomi-san/parsec-vdd)（约 5.4k）、[Easy Virtual Display](https://github.com/KtzeAbyss/Easy-Virtual-Display)（约 1.7k）、[virtual-display-rs](https://github.com/MolotovCherry/virtual-display-rs) | 为 Windows 创建可配置分辨率/刷新率的虚拟显示器，直接覆盖 PeerSpan 的虚拟屏基础 | 只创建显示器，不负责配对、串流、远端输入和窗口交接；第三方驱动二进制的再分发条款还需单独审查 |
| [Deskflow](https://github.com/deskflow/deskflow)（约 27.7k） | 让鼠标和键盘越过屏幕边缘去控制另一台电脑，输入切换体验可借鉴 | 控制的是 B 本机应用，不传输 A 的应用画面 |
| [RustDesk](https://github.com/rustdesk/rustdesk)（约 119k） | 完整的跨平台远程桌面、输入、剪贴板和自托管通信 | 以远程桌面为中心，不提供“拖入另一台电脑并与其本机窗口混排”的体验 |
| [Microsoft IddSample](https://github.com/microsoft/Windows-driver-samples/tree/main/video/IndirectDisplay) | 官方 IddCx 间接显示驱动样例，演示虚拟显示器及其 D3D 交换链帧处理 | 明确是简化样例，生产使用还需要完善稳定性、性能、安装、签名和升级机制 |

### 调研结论

GitHub 上有足够多的开源“零件”和相邻产品，可以显著降低验证成本；但截至调研日，没有发现一个成熟开源项目同时满足以下全部条件：

1. Windows A 与 Windows B 对等、角色可反转；
2. 任意普通应用仍在来源机运行；
3. 窗口可像跨物理扩展屏一样越过边缘；
4. 在目标机可操作，并能与目标机本地窗口自然共存；
5. 支持双向甚至同时投送。

因此 PeerSpan 有清晰的产品差异，但应复用成熟的媒体传输思路，避免从零发明编解码和拥塞控制。

## 3. 两种实现路径

### 路径 A：网络虚拟显示器

这是最适合 MVP 的方案，也是最接近“把 B 当作 A 的真实扩展屏”的实现。

```text
┌──────────────────── A：来源电脑 ────────────────────┐
│ 应用窗口 -> Windows 桌面 -> PeerSpan 虚拟显示器      │
│                              │                      │
│                    D3D 取帧 / 硬件编码              │
└──────────────────────────────┼──────────────────────┘
                               │ 加密的局域网媒体流
┌──────────────────── B：接收电脑 ────────────────────┐
│                    解码 / 全屏显示                   │
│ B 的鼠标键盘 ───────── 输入事件回传 ────────────────┼──> A
└─────────────────────────────────────────────────────┘
```

用户在 A 的“显示设置”中会看到一块由 PeerSpan 创建的显示器，并把它放在主屏左侧或右侧。窗口一旦被拖到这块显示器上，其像素就在 B 上显示。Windows 仍认为窗口属于 A，因此不需要迁移应用，也不需要为每种应用做适配。

优点：

- 对普通 Win32、Electron、浏览器和大多数现代桌面应用通用。
- 窗口拖动、多窗口、弹出菜单和系统任务栏主要由 A 的桌面合成器处理。
- 复杂度明显低于逐窗口代理，能最快验证延迟和用户价值。

局限：

- B 看到的是一整块远端画布。若全屏显示，远端窗口不能直接和 B 的本机窗口交错叠放。
- B 的 Alt+Tab、任务栏、窗口吸附等默认属于 B；需要明确的快捷键和焦点捕获规则。
- 两边同时把整块接收画面再次纳入采集会形成“无限镜像”，必须把 PeerSpan 接收窗口排除在捕获之外。

### 路径 B：逐窗口代理

来源端枚举可共享窗口，用户勾选后按 HWND 采集；目标端为每个远端窗口建立一个本地顶层代理窗口，并同步标题、图标、尺寸、位置、最小化、关闭请求、焦点和输入。

这条路径能实现“远端应用与本机应用混排”，但不能把 A 的原生 HWND 直接交给 B。跨边缘拖动实际上是一次视觉连续的交接：

```text
A 原生窗口 -> 检测越界 -> A 保持运行并持续采集
                         -> B 创建代理窗口并接管拖动/输入
反向越界     <- B 销毁代理窗口 <- A 恢复原生窗口位置与焦点
```

主要难点包括：

- 菜单、工具提示、对话框、拖放预览可能是独立 HWND，需要作为窗口组跟踪。
- DPI、缩放、窗口阴影、非客户区、圆角和多显示器坐标要在两边一致换算。
- 最小化后的窗口可能停止产出画面；被遮挡、硬件加速或特殊渲染的应用也存在差异。
- 文件拖放、输入法、无障碍树、任务栏缩略图和系统快捷键都不是单纯传鼠标键盘即可解决。
- 高权限窗口受 Windows UIPI 限制，普通权限进程不能可靠地向其注入输入。

建议将该模式放在虚拟扩展屏稳定之后，以“受支持应用白名单”开始，而不是第一版承诺任意窗口都完美工作。

### 路径 C：应用节点模式（App Node）

应用节点模式把没有物理显示器的 C 电脑变成一台可被 A/B 调用的远程应用主机。管理员通过 Windows 远程桌面完成首次安装，安装程序注册开机启动的 Node Service、虚拟显示驱动和用户会话 Agent。C 开机后由系统服务上线、维护虚拟显示器并发布“可启动应用目录”；配对端从应用菜单发起启动请求。

- GUI 程序由 C 的用户会话启动，窗口经逐窗口采集后作为 A 上的代理窗口显示；早期版本也可先显示 C 的整块虚拟桌面。
- 命令行程序通过 Windows ConPTY 创建伪终端，A 本地渲染 VT 输出并把键盘输入送回 C，无须采集一个黑底命令行窗口的视频。
- C 即使没有物理显示器，也可由 IddCx 虚拟显示器维持分辨率、DWM 合成和 GPU 采集环境。
- “扫描所有程序”在 Windows 上不能靠遍历全部 `.exe` 准确完成。产品应构建可启动应用目录：开始菜单快捷方式、注册表安装项、AppX/MSIX、PATH 命令和用户手工添加项，并排除卸载器、驱动、服务和系统维护工具。

无物理显示器不等于没有 Windows 用户会话。普通 GUI 程序不能从 Session 0 服务直接显示到用户桌面，因此 C 需要“系统服务 + 用户会话 Agent”双层结构。首版通过 RDP 登录完成安装和用户会话准备，安装后选择“断开连接”而不是“注销”；Node Service 继续常驻，Session Agent 留在该用户会话中。用户注销或重启后尚未重新登录时，服务仍能上线和报告状态，但 GUI 启动进入等待会话状态。真正从冷启动无人登录状态创建 GUI 会话仍需单独设计权限和凭据策略。完整需求见 [应用节点模式说明](app-node-mode.zh-CN.md)。

## 4. 推荐架构

每台电脑运行同一个对等 Agent，内部按角色启用模块：

| 模块 | 职责 |
| --- | --- |
| 发现与配对 | mDNS/局域网发现、六位配对码、设备指纹确认、受信设备列表 |
| 布局管理 | 记录对端在本机屏幕的左/右/上/下位置、物理像素、逻辑尺寸、刷新率、旋转和每显示器 DPI |
| 虚拟显示器管理 | 基于 Windows IddCx 创建、移除和配置虚拟显示器 |
| 采集与编码 | D3D11 零拷贝取帧；使用 Media Foundation、NVENC、Quick Sync 或 AMF 编码 H.264/HEVC |
| 媒体传输 | WebRTC，或“RTP/低延迟媒体流 + QUIC 控制通道”；首版优先选择成熟实现 |
| 接收与合成 | 硬件解码，显示全屏画布；后续承载多个独立代理窗口 |
| 输入路由 | 鼠标绝对/相对坐标、滚轮、键盘扫描码、焦点切换、紧急释放快捷键 |
| 剪贴板与拖放 | 首版只做文本/图片剪贴板；文件传输和跨机拖放后置 |
| 会话与恢复 | 网络切换、休眠唤醒、分辨率变化、断线恢复和崩溃后的显示器清理 |
| 应用目录 | 汇总开始菜单、注册表、AppX/MSIX、PATH 和人工配置，生成图标、名称、启动方式及权限策略 |
| 进程与窗口代理 | 在指定用户会话启动程序，关联进程树、AppUserModelID 与顶层窗口，并同步窗口生命周期 |
| 终端网关 | 用 ConPTY 托管 CMD、PowerShell 及其他 CLI，传输 UTF-8/VT 数据、尺寸变化和退出码 |
| 节点系统服务 | 支持从 RDP 会话安装，随 Windows 启动，负责设备身份、网络、虚拟显示器、策略和用户会话协调 |

### Windows 技术建议

- 产品从 Windows 10 开始支持。技术最低线定为 Windows 10 1903 x64（build 18362），因为逐窗口 Windows Graphics Capture 需要该版本能力，ConPTY 则从 Windows 10 1809 开始提供。
- 正式测试矩阵优先覆盖 Windows 10 22H2（build 19045）、Windows 10 Enterprise LTSC 2021（build 19044）和 Windows 11；比 1903 更早的 Windows 10 版本不支持。
- 虚拟显示器使用 IddCx；原型可要求用户预装一个现有虚拟显示驱动，产品版应自研并完成正式驱动签名。
- 单窗口采集使用 Windows Graphics Capture；整块虚拟屏可直接处理 IDD 交换链帧，减少一次额外拷贝。
- 图形管线采用 D3D11 纹理零拷贝到硬件编码器，避免 CPU 截图路径。
- 输入原型可使用 `SendInput`，后续再评估虚拟 HID；必须提供醒目的“释放远程控制”快捷键。
- 控制与身份通道至少使用 TLS 1.3/QUIC 或 WebRTC DTLS，不能因为只在局域网内就开放无认证输入注入。
- UI/控制层可采用 Rust + Tauri；驱动与性能敏感的图形模块使用 C++/WinRT 或 Rust `windows` crate。技术栈选择应以能稳定调用 Windows 图形和驱动 API 为准。

### 自动 DPI 适配规范

PeerSpan 自身的控制窗口、接收画布和代理窗口统一声明为 **Per-Monitor DPI Awareness V2**。协议不能只传一个宽高值，而应随显示器和窗口状态同步：物理像素尺寸、逻辑 DIP 尺寸、`dpiX/dpiY`、缩放比例、旋转方向和内容区边界。

自动适配规则：

1. **扩展屏模式**：连接时读取 B 的可用像素、DPI 与旋转，为 A 的虚拟屏协商最接近的分辨率；接收端自动缩放到 B 的可用区域，不要求两边手工设置相同缩放比例。
2. **代理窗口模式**：B 的窗口尺寸以 DIP 表示，A 按目标物理像素请求合适的捕获表面；优先重新协商/调整源窗口渲染尺寸以保持清晰度，不能调整时再由 GPU 缩放。
3. **输入坐标**：控制协议传输相对于内容区的归一化坐标，同时携带按钮、滚轮和相对移动；A 根据当前源窗口物理像素重新映射，不能直接拿 B 的屏幕坐标注入。
4. **动态切换**：窗口移入另一块不同 DPI 的显示器、系统缩放变化、RDP 连接/断开或旋转变化时，监听 `WM_DPICHANGED` 和显示配置事件，使用 Windows 建议窗口矩形，并重新协商画面尺寸。
5. **避免双重缩放**：对 DPI Unaware/System Aware 的旧程序尊重 Windows DPI 虚拟化，PeerSpan 只缩放最终捕获表面；不得再次按应用声明重复乘缩放比例。
6. **清晰度策略**：默认“清晰优先”，允许短暂重配编码分辨率；网络或 GPU 不足时降采样，但输入坐标和逻辑窗口尺寸保持不变。

自动适配可以保证窗口大小、坐标和交互一致，但不能让本身不支持高 DPI 的旧应用凭空变清晰。旧应用被 Windows 位图拉伸时仍可能模糊，产品应标记为“应用兼容性限制”，而不是 DPI 映射失败。

## 5. 可行性分级

| 能力 | 可行性 | 工程难度 | 结论 |
| --- | --- | --- | --- |
| B 作为 A 的虚拟扩展屏 | 高 | 中 | 适合作为 MVP，现有项目和官方样例已验证全部基础环节 |
| B 操作 A 虚拟屏中的窗口 | 高 | 中 | 输入坐标映射和焦点管理可控 |
| A、B 随时反转角色 | 高 | 中 | 同一 Agent 同时包含发送/接收模块即可 |
| A、B 同时向对方投送 | 中 | 高 | 要解决画面递归、输入归属、带宽翻倍和恢复逻辑 |
| 勾选单个窗口并在 B 以独立窗口显示 | 中高 | 高 | 核心链路可实现，但兼容性长尾明显 |
| C 无物理显示器时上线并提供虚拟桌面 | 高 | 中 | IddCx 和开机系统服务可以覆盖，仍需处理驱动签名及异常清理 |
| A 浏览 C 的应用目录并远程启动 | 高 | 中高 | 应用发现和普通进程启动可控，但需要去重、权限、会话及审计设计 |
| 在 A 使用 C 的命令行程序 | 高 | 中 | ConPTY 比视频采集终端更可靠，可保留复制、调整尺寸和退出码语义 |
| C 的 GUI 程序作为 A 的独立窗口 | 中高 | 高 | 依赖逐窗口代理和一个已登录的交互式用户会话 |
| 不同分辨率和 DPI 间自动适配 | 高 | 中高 | Per-Monitor V2、DIP/像素分离及归一化输入可实现；旧应用清晰度受其 DPI 能力限制 |
| C 从冷启动、无人登录状态提供任意 GUI | 中低 | 很高 | Windows 会话隔离、凭据保管和锁屏捕获使其不适合作为首版承诺 |
| 单窗口无缝跨边缘且与本机窗口混排 | 中 | 很高 | 需要代理窗口、窗口组跟踪和复杂状态机 |
| 任意应用、UAC、DRM、反作弊游戏全部支持 | 低 | 极高 | 不应作为产品承诺，应明确排除或逐项兼容 |
| Windows/macOS/Linux 全平台互相投送 | 中 | 极高 | 各平台捕获、输入、权限和窗口系统差异太大，应在 Windows 稳定后再做 |

## 6. 必须正视的产品边界

1. **受保护内容**：DRM 视频、密码/安全桌面、部分反作弊和独占全屏内容可能只能得到黑屏，或禁止输入注入。
2. **权限边界**：B 操作 A 上的管理员窗口时，来源端需要匹配权限；UAC 安全桌面不能按普通桌面方式控制。
3. **焦点归属**：键盘输入在任何时刻必须明确属于 A 或 B，切换时需要状态提示，断线时必须自动归还本机。
4. **体验依赖网络**：鼠标操作对抖动比视频更敏感。编码帧队列应宁可丢帧也不要持续积压。
5. **驱动发布成本**：生产级 Windows 显示驱动涉及 WDK、签名、安装升级、蓝屏风险控制和硬件实验室验证，不只是普通桌面软件打包。
6. **开源许可**：已确认 PeerSpan 用户态代码采用 GPLv3 only，并固定 Sunshine/Moonlight 完整对应源码；微软 IddCx 派生驱动继续按 MS-PL 作为独立二进制聚合。Parsec VDD 管理器仓库的许可证仍不能自动代表其所携带驱动二进制的再分发许可。
7. **应用节点权限**：远程启动命令行本质上接近远程代码执行。默认只应发布白名单应用；远程 Shell、管理员程序、任意参数和自定义工作目录必须逐项授权并记录审计日志。
8. **Windows 会话隔离**：开机系统服务运行在 Session 0，不能直接承载普通 GUI。应用节点需要用户会话 Agent，且首版 GUI 投送要求该用户已登录、未处于安全桌面。
9. **RDP 会话生命周期**：断开 RDP 通常保留进程，注销则销毁用户会话。组策略还可能自动结束断开的会话，因此安装器应检查会话超时策略，节点 UI 也要明确显示“服务在线/GUI 会话可用”两个独立状态。
10. **旧应用 DPI 兼容性**：DPI Unaware 或只支持 System DPI 的应用可能由 Windows 做位图拉伸。PeerSpan 可以正确映射尺寸和输入，但无法保证这些应用在 150%/200% 屏幕上与原生 Per-Monitor V2 应用一样锐利。

## 7. 建议的 MVP

### 范围

- 两台 Windows 10 1903 x64 或更高版本的电脑，同一局域网；正式验收使用 Windows 10 22H2/LTSC 2021 和 Windows 11。
- 自动发现后用配对码确认，双方持久保存设备公钥。
- A 创建一块 1920×1080、60 Hz 的虚拟显示器，可配置在左或右。
- B 以无边框窗口或全屏方式显示该虚拟屏，并回传鼠标、键盘和文本剪贴板。
- 自动识别双方显示器的 DPI、缩放和旋转，用户无需先把两边设成相同百分比。
- 窗口从 A 物理屏拖入 B 后可继续操作；关闭连接时自动把遗留窗口移回 A 主屏。
- 同一安装包允许用户选择 A -> B 或 B -> A，首版不要求两个方向同时工作。
- 有线千兆或 Wi-Fi 6 环境下，将交互端到端延迟中位数低于 80 ms 作为目标，而不是宣传承诺。

### 明确不做

- 目标机原生代理窗口和本机窗口混排。
- 跨机文件拖放、USB、摄像头和完整音频设备重定向。
- HDR、4K 高刷新率、独占全屏游戏。
- UAC 安全桌面、DRM/受保护内容和反作弊场景。
- 公网穿透、账号云服务和移动端。

### 验收场景

1. A、B 在 30 秒内完成发现和首次配对。
2. A 的显示设置中出现 PeerSpan 虚拟屏，并可布置在主屏右侧。
3. 记事本、资源管理器、浏览器和 VS Code 可从 A 拖到 B，B 能完成点击、滚动和键盘输入。
4. 断开 B、B 休眠或网络中断后，A 不留下不可见的窗口，输入控制在 1 秒内自动释放。
5. 接收端不会被再次捕获，从而避免双向会话中的递归画面。
6. 未配对设备无法看见画面或注入输入。
7. 在 A 1080p/100%、B 4K/150% 以及 A 125%、B 175% 的组合下，窗口大小和鼠标落点正确；切换 B 缩放或旋转后无需重连即可恢复。

## 8. 应用节点模式里程碑

应用节点模式不是基础扩展屏 MVP 的隐含功能，而是紧随其后的独立里程碑：

- C 没有物理显示器，安装 PeerSpan 后可启用“应用节点模式”。
- 管理员可通过 Windows 远程桌面完成安装和配对；安装程序注册受限 Node Service、虚拟显示驱动及用户 Session Agent。
- C 开机后以受限系统服务上线并创建虚拟显示器；GUI 程序由已登录用户的 Session Agent 启动。RDP 应断开而非注销。
- A/B 配对后显示 C 的可搜索应用菜单，包含名称、图标、来源、GUI/终端类型和权限提示。
- 普通 GUI 应用可启动、显示、输入、最小化、关闭和重新连接；纯 CLI 应用在 A/B 的原生终端视图中运行。
- 代理窗口自动适配 A/B/C 的每显示器 DPI；窗口跨越不同缩放显示器时，逻辑尺寸、清晰度策略和输入坐标同步更新。
- C 本地策略可选择“仅允许列表”或“发布扫描到的全部普通应用”；远程 Shell 和提权程序始终需要独立授权。
- 终止远端窗口时，用户可选择只关闭代理窗口或同时结束 C 上的进程；默认行为必须清晰可见。

验收时至少覆盖：通过 RDP 在 C 安装后断开会话；从 A 启动 C 上的记事本并编辑保存文件；从 A 打开 C 上的 PowerShell/CMD，运行命令、调整终端尺寸并获取退出码；C 全程不连接物理显示器。注销 C 用户后，A 应显示“节点服务在线，GUI 会话不可用”，而不是启动失败或黑屏。

## 9. 推荐研发顺序

1. **技术尖刺**：不写完整 UI，打通“虚拟屏一帧 -> 硬件编码 -> B 解码显示 -> 鼠标回传”。
2. **单向 MVP**：加入配对、布局、键盘、剪贴板、断线恢复、安装和诊断日志。
3. **应用节点基础**：加入开机服务、虚拟显示器、应用目录、权限策略和 ConPTY 远程终端。
4. **节点 GUI 应用**：只支持普通非提权 Win32/Electron 应用，建立启动关联、窗口组和代理协议。
5. **对等化**：同一程序支持角色反转，验证双向但非同时的稳定性。
6. **双向同时会话**：加入焦点仲裁、接收窗口捕获排除和带宽策略。
7. **无缝交接**：完善边缘拖动、DPI、菜单/对话框、任务栏集成和文件拖放。
8. **无人值守 GUI 会话**：最后评估专用节点账户、登录会话建立、凭据保护和锁屏策略，不默认启用。

## 10. 名称

**PeerSpan（邻屏）**：

- `Peer` 表示 A、B 是对等节点，而不是固定服务器和瘦客户端。
- `Span` 表示桌面和窗口跨越设备边界。
- 中文副名“邻屏”突出局域网内相邻电脑扩展屏的使用场景。
- 标语：**窗口跨屏，算力留在原机。**

GitHub 仓库名检索在调研日未发现名为 `PeerSpan` 的仓库，但正式发布前仍应继续检查商标、域名、软件商店和包管理器中的名称冲突。
