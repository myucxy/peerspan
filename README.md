# PeerSpan（邻屏）

> 窗口跨屏，算力留在原机。

PeerSpan 是一个局域网内的对等桌面扩展和远程应用方案。A、B 两台 Windows 电脑都安装同一个客户端后，可以把对方当作一块可交互的扩展屏；也可以将没有物理显示器的 C 配置为应用节点，从 A/B 的菜单中启动 C 上的软件。窗口的画面和输入跨机器传输，但进程、CPU/GPU 计算、文件访问和应用状态始终保留在窗口原来的电脑上。

## 产品形态

PeerSpan 计划提供三种逐步演进的工作模式：

1. **扩展屏模式（首个 MVP）**：在来源电脑上创建虚拟显示器，另一台电脑显示并控制这块虚拟显示器。用户可直接把任意普通窗口拖入该显示器。
2. **窗口模式（后续版本）**：用户勾选一个应用，远端电脑创建对应的代理窗口，使远端应用能与本机窗口混排、移动、最小化和切换。
3. **应用节点模式（App Node）**：把没有物理显示器的电脑变成远程应用主机。配对端可浏览该节点的应用目录，远程启动 GUI 或命令行程序，并把程序窗口或终端显示在本机。

首个版本只需实现第一种模式，就可以验证最核心的体验：

```text
A 上启动应用 -> 拖入 A 的虚拟扩展屏 -> B 显示并操作
                                      -> 应用仍在 A 上运行
```

同一个 PeerSpan 实例同时具备发送端和接收端能力，所以角色可以反转。双向同时投送属于后续能力，需要额外处理输入焦点和画面递归。

应用节点模式中的 C 电脑不需要连接物理显示器。管理员先通过 Windows 远程桌面登录 C，安装 PeerSpan Node Service、虚拟显示驱动和用户会话 Agent；之后 Node Service 随系统启动并保持节点在线。A 配对 C 后会看到可搜索的应用菜单；启动 GUI 程序时，程序仍在 C 的 RDP/控制台用户会话中运行并将窗口传到 A；启动纯命令行程序时，A 使用本地终端界面显示 C 上 ConPTY 会话的输出。

Windows 服务本身运行在 Session 0，不能直接承载普通 GUI。安装完成后应“断开”远程桌面而不是“注销”，让用户会话和 Session Agent 保持运行；若用户注销或机器重启后尚未重新登录，Node Service 仍在线，但 GUI 启动暂时进入“等待用户会话”状态。

## 当前结论

- **技术上可以实现**，Windows 现有的间接显示驱动、窗口/屏幕采集、硬件视频编码和输入注入接口已经覆盖主要基础能力。
- **扩展屏模式可行性高**，适合作为第一版；它不需要真正把进程或窗口对象迁移到另一台电脑。
- **像原生窗口一样无缝跨边缘拖动可行，但工程难度高**。两套 Windows 桌面无法共享同一个原生窗口对象，需要在远端创建代理窗口并同步生命周期。
- 现有开源项目分别解决了虚拟显示器、低延迟串流、远程应用窗口或跨机键鼠，但尚未发现一个成熟项目完整覆盖 PeerSpan 的 Windows 双向体验。

## 建议的首发范围

- Windows 10 1903 x64 或更高版本；正式测试 Windows 10 22H2、Windows 10 Enterprise LTSC 2021 和 Windows 11
- 自动发现、配对码确认和加密连接
- 单向 1080p60 虚拟扩展屏
- 自动适配每台电脑的 DPI、系统缩放和显示器旋转，覆盖常见的 100%/125%/150%/175%/200% 缩放组合
- 鼠标、键盘和剪贴板回传
- A -> B 与 B -> A 均可建立，但首版不要求同时开启
- 有线千兆或 Wi-Fi 6 环境下，以端到端交互延迟低于 80 ms 为验收目标
- 暂不支持 DRM/受保护画面、UAC 安全桌面、反作弊游戏、HDR 和独占全屏

应用节点模式作为紧随扩展屏 MVP 的第二个里程碑，增加无物理显示器运行、应用目录、远程启动、GUI 窗口投送和 ConPTY 终端。

## 开发环境约定

- 系统级开发环境统一放在 `D:\Dev\Env`。
- 开发前优先检查并复用该目录中已有的 SDK、编译器、运行时和工具链，保持现有的目录组织与命名习惯。
- 开发过程中若缺少必要环境，可按该目录的现有习惯安装到 `D:\Dev\Env`；不得随意覆盖、移动或删除已有环境。
- 每次新增或调整环境后，必须在项目说明文档中记录工具名称、版本、安装路径、用途、所需环境变量以及安装和验证命令，确保后续开发可以复现。
- 项目自身可由包管理器还原的依赖仍应通过项目配置文件管理，不将生成的依赖目录提交为系统环境。

## 状态

项目已进入 MVP 开发阶段，当前完成了：

- React/Vite/Tauri 桌面客户端框架与主要交互界面；
- 可持久化的设备身份、偏好和可信设备信息；Ed25519 私钥由当前 Windows 用户的 DPAPI 加密保护；
- 基于 mDNS 的局域网发现与定时刷新；
- 六位配对码、SPAKE2 密钥协商、XChaCha20-Poly1305 加密和 Ed25519 身份签名；
- DPI 无关的输入坐标映射与版本化控制协议基础；
- 可无错误构建、打包和测试签名的 IddCx 1.4 单屏 1080p60 驱动原型；
- Rust、TypeScript、Vitest、Web 生产构建和 Tauri Release 构建验证。

当前重点是 Windows 原生链路：驱动安装与生命周期控制、把 IddCx/D3D11 帧送入硬件编码器、认证媒体/控制通道、远端输入与断连恢复。尚未接通这些能力时，客户端会明确显示不可用，不会用模拟状态代替真实会话。

## 本地开发

环境路径和版本以 [开发环境记录](docs/development-environment.zh-CN.md) 为准。新终端中先加载固定 Rust 目录，再执行验证：

```powershell
$env:RUSTUP_HOME = "D:\Dev\Env\Rust\rustup"
$env:CARGO_HOME = "D:\Dev\Env\Rust\cargo"
$env:PATH = "D:\Dev\Env\Rust\cargo\bin;$env:PATH"

npm install
cargo test --workspace
npm run typecheck
npm test
npm run build
```
